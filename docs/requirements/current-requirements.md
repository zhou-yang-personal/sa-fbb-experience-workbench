# SA FBB Experience Workbench｜当前需求基线

## 下一版目标态需求基线（2026-08-28，已确认）

实现进度说明：1.0.67 已落地本基线中的公共 `用户 × App × 小时` 聚合底座、加权再聚合状态、任务依赖顺序和版本化断点；全景洞察的其余指标/App/用户图表仍按本文件继续迭代，不能因底座完成而宣称整份目标态已全部实现。

本节汇总 1.0.59 之后完成评审的产品、指标、规则、聚合和交互需求。它描述下一版目标态，不表示当前版本已经实现。若与下方历史版本要求冲突，以本节为准；兼容代码可以保留，但不得继续作为普通操作者的默认主链路。

### 1. 产品定位与分析顺序

产品是本地家宽应用体验分析工作台，不是普通 BI、异常告警大屏或实时监控平台。统一分析顺序为：

```text
数据覆盖
→ 整体规模和分布
→ 指标 / App / 用户全景
→ 高亮质差用户和质差 App
→ 用户侧 / 网络路径侧问题证据
→ Cable vs FTTH 专项对比
→ 潜客机会
→ CRM 等外部数据资格校验
```

总览必须先讲清完整现状，再高亮问题；网络位置、问题侧和商业行动结论不得在第一层提前出现。离线批次趋势不得包装成实时监控、实时告警、预测故障或自动闭环。

### 2. 傻瓜式信息架构

普通模式一级导航收敛为五项：

1. 全景洞察；
2. 质差分析；
3. Cable vs FTTH；
4. 潜客机会；
5. 数据中心。

“设置”和“帮助与诊断”作为次级入口。现有 App 体验和用户洞察收进全景洞察页签；自动发现、问题调查、保存调查和网络路径证据收进质差分析；规则配置收进设置；系统诊断退出主导航。

每页最多一个高亮主操作和两个普通次操作。不可用操作应隐藏并用状态说明原因，不展示成排灰色按钮。普通模式不得渲染 RAW/DWD/ADS、Registry、物理表、connection ID、Structured API、ADS 物化、单步 SQL、Module Ready 等开发者控制面；专家模式需要在设置中显式开启并显示风险提示。

应用启动继续保持零数据库访问。用户点击“继续分析”或选择批次后，视为授权建立一次分析会话；会话内页面切换可以自动读取有界 DWS/ADS 并复用缓存，但不得扫描 RAW、隐式重聚合或启动长任务。普通页面不再反复展示批次选择器、analysis_run_id、运行就绪状态和“加载当前看板”按钮；系统默认选择所选批次最新成功或降级且可分析的运行。

首页按状态只提供唯一推荐动作：无数据时导入；批次就绪时继续分析；任务运行中时查看进度；任务中断时继续未完成任务；失败时查看并处理；仅 RAW 时生成分析结果。系统根据真实前置状态选择从 DWS/ADS 续跑或从 RAW 重建，普通用户不同时面对两个技术按钮。

### 3. 数据中心与导入

新建分析采用“选择文件 → 确认规则 → 开始导入并生成分析结果”三步向导。默认隐藏 LOAD DATA / Streaming INSERT、手工 Quality Gate、单步 CLEAN/DWS/ADS、SQL 脚本和 Registry。每次 TCP/Game 导入仍需明确确认已发布接入规则版本，系统可以推荐默认版本但不得静默替用户确认。

批次库只展示业务名称、数据日期、数据规模、状态和一个推荐操作。已就绪批次打开分析，运行中批次查看进度，中断批次继续任务，失败批次查看并处理，仅 RAW 批次生成结果。删除、重命名、从 RAW 重建等低频操作进入行尾更多菜单；运行中批次禁止删除。

### 4. 接入识别与分析用户

Cable/FTTH 继续使用版本化 IPv4 规则。命中明确网段使用该网段结果；`Others` 是未命中任何显式网段的剩余有效 IP 集合，必须在每个规则版本中显式配置归属，当前业务配置为 Cable。Others 不得写死在 React、Rust、SQL 或数据库默认值中，必须参与草稿、验证、预览、发布、批次绑定和证据追溯。非法、空、`--` 等 IP 保持不可用，不得聚合为共同 UNKNOWN 用户。

当前阶段统一以规范化有效 IP 作为分析用户标志：优先使用可解析为 IP 的 User Account，否则回退到 Local IP Address；同一 analysis run 内按 IP 去重。MAC 缺失和身份可信度不得阻断体验、App、时间、接入或潜客分析。普通文案必须使用“分析用户（按 IP 去重）”，不得表述为已确认客户、家庭或可直接营销对象；跨批次身份和正式营销仍需 CRM 映射。

### 5. 数据状态语义

所有 SQL、Rust、API、图表、表格和导出必须区分真实 0、NULL/缺失、未导入、不可用、有限样本、极少样本、未知字段值以及 Others 配置后的接入类型。Game 文件未导入时，Game 时长、MOS 和相关潜客规则显示未导入/不可用，不得以 0 参与分布、质差或机会结论。

### 6. 全景洞察

全景洞察由“指标视角、App 视角、用户视角”三个基础页签组成。允许视角之间存在重复图表，数据与分析逻辑完整性优先，代码层复用查询和组件。

指标视角一级指标为流量、使用时长、上行速率、下行速率、视频有效下载速率/平均下载速率保障能力、时延和丢包。vMOS 不作为独立一级指标，只作为视频体验辅助证据。每个指标至少提供整体均值/中位数、分档用户分布、App 整体排序、重度/普通/轻度用户分布、时间趋势、问题高亮、分子分母、样本和单位。

App 视角第一层必须按唯一 App 统计，不出现 Cable/FTTH 标签、系列或颜色；展示 App 数量、覆盖用户、观测用户、有效观测、流量、时长、速率、时延、丢包和体验状态。选择 App 后才按接入、时间、用户、指标和 Server IP 下钻。唯一 App 状态合计必须与唯一 App 总数一致；`App × Access Type` 是独立下钻粒度，不能与 App 总数混用，也不能相加多个接入组合的去重用户数获得 App 用户总数。修正 `HEALTHY`/`NORMAL` 状态枚举不一致，并移除“规则标记 App”等内部文案。

用户视角取消综合 demand_score 和“高/中/轻/低需求”。改为日均流量、日均有效时长、日均视频观测记录、日均高峰期时长、独立 Game 时长、主要 App 数量、质差 App 数量和单 App/多 App 质差用户等可解释分布。

### 7. 单位、语言和解释

所有图表、筛选、状态、证据表和 PDF 支持中英文。图表标题、坐标轴、Tooltip 和证据表必须明确单位；流量图最大值小于 1000 GB 时统一显示 GB，达到后统一显示 TB，并注明 `1 TB = 1000 GB`。空值显示 `—/不可用`，不得伪装为 `0 GB`。每张图下方提供简短说明：回答的问题、计算口径、分子分母、解读方法、样本或覆盖限制。

### 8. 质差用户、质差 App 与问题侧

质差观测由版本化 App Experience Profile 判定，不同 App 类型使用不同主指标。用户 × App 持续质差启动默认值为：有效观测不少于 5 条、质差观测不少于 2 条、质差观测占比不少于 30%，并至少涉及 2 个时间窗口或 2 个活跃日。用户整体区分曾受影响、单 App 持续质差、多 App 持续质差和严重质差。

唯一 App 的启动默认状态为：质差观测占比达到 10% 或持续质差用户占比达到 5% 时关注；两者分别达到 20% 和 10% 时为问题；两者分别达到 40% 和 20%，或严重用户占比达到 10% 时为严重。问题 App 第一层按唯一 App 统计，不按接入组合排名。

问题侧不得强制二选一，至少保留“更偏用户侧、更偏网络/路径侧、双侧均异常、App/内容源相关、证据不足”。用户侧证据包括 Subscriber Side RTT、User Side 上下行丢包、Wi-Fi Delay、Access-side Delay 和用户/网络差值；网络/路径侧证据包括 Network Side RTT、Network Side 上下行丢包以及多用户、多 App、同时间共同异常。vMOS、有效下载速率、流畅度和建连指标首先是体验结果，不能单独定位问题侧。

问题侧启动默认值为：侧向有效观测不少于 5 条、异常证据率不少于 30%、主导侧相差不少于 15 个百分点。少数用户多 App 异常偏用户/家庭侧，多用户单 App 异常偏 App/CDN/内容源，多用户多 App 同时异常偏网络/公共路径，少数用户单 App 异常保持孤立或证据不足。Network Side 指标不得包装为已确认 BRAS/OLT/PON 故障。

全景总览移除网络侧可疑聚集、BRAS/OLT/PON 覆盖、热点和问题侧结论。当前仅有一个可识别 BRAS、无有效 OLT/PON，不能生成设备级热点结论；网络/路径证据只在质差下钻中出现。

### 9. Cable vs FTTH 专项

Cable vs FTTH 保留一级入口，但不得在全景第一层提前拆分。专项必须在同日期、时间、App、使用强度、单位和分母下比较，展示完整 Cable/FTTH 分布并高亮差异，而不是只展示 Cable 较差对象。所有对比必须显示样本和可比性。页面完整章节、匹配基线、指标差异阈值、用户/App 关系以及进入迁转证据的规则仍需在实施中以可配置结构落地，并通过真实数据预览校准。

### 10. 潜客类型与商业资格

一级潜客类型固定为：Cable-to-FTTH 迁转、带宽升档、家庭组网/AP/Mesh、App Bundle。一个分析用户可以命中多个类型；底层使用“用户 × 机会类型”的多行模型，不再用单一 Lead Type 同时表达类型、等级、状态和动作。组合套餐是多个机会的产品组装结果，不是第五种潜客类型。

故障修复、网络建设、普通观察、身份不可信、高价值等级不属于潜客类型。当前 SA 数据只输出“体验和使用数据驱动的机会候选 IP”。正式营销资格需要 CRM 客户匹配、当前套餐、FTTH 覆盖、可售产品、合约、欠费、黑名单、可触达和合规状态；匹配失败只标记待匹配，不得从机会池删除。删除 A0 身份不可信分类。

迁转候选启动默认值：Cable、至少 2 个有效分析日和 10 条有效观测，并命中日均流量不少于 5 GB、日均有效时长不少于 3 小时、日均高峰时长不少于 1.5 小时、日均视频观测不少于 20 条中的任一项。

带宽升档候选启动默认值：满足基础样本，并在日均流量不少于 10 GB、日均有效时长不少于 4 小时、日均高峰时长不少于 2 小时、日均视频观测不少于 30 条、高带宽 App 活跃不少于 3 天中命中至少两项。没有 CRM 套餐速率时只输出候选，不推荐具体速率档。

家庭组网候选首先要求 Wi-Fi/家庭侧相关指标覆盖率不少于 30%，再依据 Wi-Fi Delay 不少于 30 ms、用户侧 RTT 比网络侧高不少于 30 ms、用户侧丢包比网络侧高不少于 1 个百分点或现象持续不少于 3 个活跃日生成候选。覆盖不足显示不可识别，不得显示 0 名潜客；没有终端、CPE和家庭覆盖数据时不推荐具体 Mesh 节点数。

App Bundle 公共启动默认值为 App 活跃不少于 3 天，并命中日均时长不少于 30 分钟、App 流量占比不少于 20%、日均观测不少于 10 条中的任一项。Bundle 与 App/App 类别、产品有效期、适用接入和套餐的关系来自版本化产品目录，不在代码中写死品牌或权益。

### 11. 版本化配置与启动默认值

所有影响分档、样本、质差、问题 App、问题侧和潜客判断的阈值都必须配置化，分为时间/高峰期、用户行为分档、体验指标、样本规则、问题 App、问题侧、潜客规则和 Bundle 产品目录。配置支持草稿、复制、编辑、校验、影响预览、发布、不可变版本、analysis run 绑定和恢复系统建议值。预览只读取 DWS/ADS，显示新旧规则下分档、样本、问题 App、潜客类型、类型重叠和不可判断人数，不扫描 RAW，也不自动发布。

启动默认值如下，正式发布前必须用真实批次分布预览：高峰期 20:00–23:00；最低有效分析天数 2 天；用户最低有效观测 3 条；潜客最低观测 10 条；样本充分为 30 名合格用户且 100 条有效观测；有限样本为 10 名用户且 30 条观测，以下为极少样本。

日均流量分档为 `<1 / 1–5 / 5–15 / ≥15 GB`；日均有效时长为 `<1 / 1–3 / 3–6 / ≥6 小时`；日均高峰时长为 `<0.5 / 0.5–1.5 / 1.5–3 / ≥3 小时`；日均视频观测为 `1–5 / 6–20 / 21–50 / >50`，真实 0 单列。下行速率分档为 `<1 / 1–5 / 5–20 / 20–50 / ≥50 Mbps`；上行速率为 `<0.5 / 0.5–2 / 2–5 / 5–20 / ≥20 Mbps`；RTT 为 `<30 / 30–60 / 60–100 / 100–200 / ≥200 ms`；丢包为 `0 / 0–0.5% / 0.5–1% / 1–3% / ≥3%`。

### 12. 聚合、任务与恢复

聚合按可复用底座和指标族拆分，不按每张图重复扫描 DWD。主路径为标准 DWD → 用户 × App × 时间公共 DWS → 指标/App/用户/质差/Cable-FTTH/潜客 DWS/ADS。任务采用父流水线和独立子任务，每个子任务有状态、日志、耗时、checkpoint和选择性重跑；已成功分片不重复执行，新结果完成前保留旧成功结果，完成后原子发布。同一 MySQL 实例限制重型聚合并发。

小时聚合继续按日期/小时分片独立提交，禁止千万行整批单事务；MySQL/应用重启后遗留运行标记 interrupted，从未完成 checkpoint 恢复。心跳只能表示应用线程可写日志，真实 SQL 活动需要连接和语句证据。普通任务页只展示文件导入、数据检查、数据清洗、生成分析结果和准备看板等业务阶段，SQL明细进入专家技术详情。

修改图表分档只重跑分布 ADS；修改样本或体验规则重跑相关体验 DWS/ADS；修改潜客规则只重跑潜客 ADS；修改 Bundle 映射只重跑 Bundle ADS；修改 IP 规则需要从 CLEAN/DWD 重建。发布前必须明确重跑范围和影响页面。

### 13. 导出与性能边界

全部看板继续支持图表 PDF，锁定批次、运行和筛选，默认导出所有非空图表且不含明细表，记录本地生成时间、时区、数据源、空图和失败项。潜客明细使用后端分页和 CSV 导出，并区分机会候选 IP 与正式营销名单。

前端不得拉取大明细后排序；页面和导出优先读取 ADS，跨维分析读取 DWS，Server IP 只在受控 App/用户范围内解析，不做无边界全量 explosion。1 GB+ 导入和 1300 万行聚合必须继续使用分片、checkpoint、命名锁和旧结果保护；MySQL 配置调优不能替代 SQL/事务改造。

### 14. 待验证而非待设计项

以下内容已有方向但需要真实数据验证后发布：Download Fluency 的正式业务语义；上行/下行速率字段的覆盖率和可用口径；Cable vs FTTH 匹配基线和差异阈值；上述启动默认值在当前 1300 万行批次上的命中分布。验证不足时显示不可用或试行规则，不得把默认值描述为行业定论。

## 1.0.59 全量洞察要求

- 体验总览必须覆盖当前可用的完整 App、接入、时间、用户、网络证据和商业机会结构，并在完整分布中高亮问题项；不得只展示问题卡片。
- 应用体验必须保留全部 App × 接入类型组合，状态只能来自本次 analysis run 绑定策略的样本与关注等级；正常、关注、严重、样本不足和未分级必须可区分。
- App 组合必须可查看业务规模、分子、分母、有效样本、差体验观测、持续/严重体验、主要证据、策略版本并进入共享分析上下文。
- 加载看板不得执行 migration，不得扫描 RAW，不得因历史 `NULL` 或类型异常退出 EXE；单数据集失败必须显示为部分失败并允许继续使用其他结果。
- 全量总览先解释整体规模、业务分布、体验现状和接入趋势；BRAS / OLT / PON、网络侧可疑聚集等定位信息，以及 A1 候选、A2 先修障等行动/机会结论，不应出现在总览第一阶段。定位信息只在用户主动进入“网络 / 路径证据”或问题调查后展示，机会与行动结论只在后续商业机会阶段展示。

### 待确认：App 数量与状态构成粒度（2026-08-28）

当前实测页面同时出现：

- 全部 App：131（按 `app_name` 去重）；
- 状态构成：问题 83、关注 1、样本不足 162，合计 246（按 `App × Access Type` 组合计数）。

这两个数字分别正确描述不同粒度，但“全部 App 体验状态构成”的文案会让操作者误以为状态合计必须等于 131，属于高优先级指标语义问题。在确认最终方案前不得仅通过改标题或强行对齐数字掩盖粒度差异。

待确认方案：

1. 唯一 App 视图按 `app_name` 去重，状态合计必须等于全部 App；同一 App 多个接入组合的汇总优先级建议为 `SEVERE > ATTENTION > HEALTHY > INSUFFICIENT_SAMPLE > UNCLASSIFIED`。
2. `App × Access Type` 组合视图单独显示组合总数和各状态构成，并保留 Cable / FTTH 的差异证据。
3. “规则标记 App”文案需改为可理解名称，并显示命中的策略版本、阈值、分子、分母及具体接入组合。
4. 实现前需修正状态枚举一致性：ADS SQL 输出健康状态为 `HEALTHY`，当前前端识别值包含 `NORMAL`，二者不一致可能把健康对象错误归入未分级。

### 待确认：网络侧可疑聚集指标语义（2026-08-28）

### 已确认：取消综合“需求评分”，拆分为可解释的用户行为分布（2026-08-28）

### 已确认：当前阶段以 IP 作为用户分析标志（2026-08-28）

13. RAW 导入不得把 0 行结果标记为成功；Probe、字段映射和两种导入模式必须使用同一分隔符判断，失败信息必须直接展示 RAW 行数、MySQL warning 或 Quality Gate 失败项。
14. `LOAD DATA LOCAL INFILE` 必须由客户端流式提供当前所选 CSV 的内容；本地文件处理器只允许该文件的规范路径，拒绝服务端请求其他路径，并在单次语句后移除。
15. RAW 长时间导入必须持续提供可观测进度：至少包含客户端已处理字节、文件总大小、百分比、批次 ID，并区分文件传输与 MySQL 解析/提交等待；连续无变化不得静默。
16. 应用启动、恢复或选择历史批次、切换分析页时不得自动执行批次表准备、RAW 全表计数或批量看板查询；分析任务必须由用户明确启动，展示执行范围、进度、当前步骤、失败和重试，并允许停止尚未开始的后续步骤。
17. 流水线日志必须按 sequence 可靠增量读取并去重，不得因重叠轮询重复展示；RAW 导入以外的长步骤也必须定期写入存活心跳和步骤耗时。前台必须能区分“任务仍运行但无内部百分比”“日志刷新失败”“用户暂停刷新”和“心跳延迟”。日志时间必须以 UTC 持久化并按本地 PC 时区显示，复制日志时必须带出时区标识。
18. 进入系统诊断页不得自动执行 Catalog、批次表计数、模块、映射、质量或 ETL 查询；诊断必须由用户显式启动并展示串行步骤、进度、失败和停止后续检查入口。一次诊断不得为 Registry 和模块状态重复刷新大表计数，高级排错和执行日志必须展开后才挂载。
19. 批次的 RAW 导入成功不得等同于完整分析成功。历史批次必须分别展示 RAW 与流水线状态，选择批次时同步其最新流水线和 `analysis_run_id`，并可恢复该流水线的完整日志；看板空数组或全 0 指标必须显示“无可用 CLEAN/DWS/ADS 证据”，不得显示 `SUCCESS`。
20. 已完成 RAW、Quality Gate 和 CLEAN 的历史批次必须可显式从 DWS/ADS 续跑，不重读 CSV 或重建 RAW。续跑必须覆盖完整 DWS、基础 ADS、App Rank、小时趋势、网络热点、用户画像、Lead Evidence、可选 Final Lead 和 Module Ready，并展示子阶段日志。同批次存在活动 MySQL SQL 时必须拒绝并发接管；批次准备、Registry 和 Module Ready 常规路径不得隐式扫描大表精确 `COUNT(*)`。
21. 六类决策看板必须提供显式的“导出全部图表 PDF”任务。默认导出当前批次、`analysis_run_id` 和筛选条件下的全部非空图表，不包含明细表；任务必须顺序加载聚合数据、显示进度与失败、允许停止尚未开始的步骤，并在报告中记录本地生成时间、时区、DWS/ADS 来源和被跳过的空图。
22. IP 规则集必须把 `Others` 作为规则版本中的显式组成部分：`Others` 指未命中上方任何已配置 IP 网段的剩余 IP 集合，用户必须在规则页明确配置这部分最终归属的制式（当前业务选择 Cable），不得由前端、后端、数据库默认值或 SQL 隐式写死。该选择必须参与草稿、验证、预览、发布、批次绑定和证据追溯；接入制式分析结果不再使用 UNKNOWN 承接正常的未命中人群。未导入独立 Game 文件时，游戏时长与 MOS 必须显示为“未导入/不可用”，不得用数值 0 参与结论。
23. Lead 分层和用户分布图必须来自完整 ADS 总体聚合，不得用分页明细或 Top N 代替总体；多日小时趋势应默认压缩为按活跃用户加权的典型 24 小时曲线，同时保留小时证据明细。
24. 应用启动必须做到零数据库访问：不得自动加载批次列表、恢复流水线、查询 analysis run 或执行就绪检查。所有 MySQL 操作必须由用户点击明确动作后开始；启动、正常退出、Tauri 运行错误和 Rust panic 应写入不含凭据与客户数据的本地运行日志。
25. 已成功导入 RAW 的 TCP/Game 批次必须支持显式从 RAW 重建分析结果：跳过 CSV 和 RAW 导入，重新执行分块 CLEAN/DWD、CLEAN 后质量验证、DWS、ADS、V2、可选 Final Lead 和 Module Ready，并创建新的 analysis run。RAW→CLEAN 必须使用有界主键分片和独立提交，批量写入期间避免逐行维护全部二级索引。核心 SQL 脚本中的每条语句必须在实时 pipeline 日志中展示 RUNNING/SUCCESS/FAILED、执行耗时、影响行数和有界语句摘要；同批次活动 SQL 存在时必须拒绝并发重建。
26. 千万行 DWD 的小时体验聚合不得使用整批单事务。必须按有界日期/小时分片独立提交，持久化成功 checkpoint，支持进程或 MySQL 重启后从未完成分片继续；同一 MySQL 实例只允许一个 DWS/ADS 聚合任务，运行未成功前不得把部分结果标记为可分析。

## 2.1 已确认的下一版产品需求

1. 接入制式只把明确命中的 FTTH IP 网段识别为 FTTH；未命中集合由规则页中的 `Others` 显式决定当前规则版本应归为哪种制式。`Others` 是“剩余集合”，不是固定写死的第三种接入制式。
2. 当前业务规则将 `Others` 配置为 Cable，因此重新生成 CLEAN/DWS/ADS 后，正常分析结果中不应再出现接入制式 UNKNOWN。
3. 身份可信度在当前阶段弱化：不得作为体验总览的核心结论，不得阻断 App、时间、网络和接入制式分析；只在用户明细或最终营销资格阶段作为辅助提示。
4. 所有看板、图表、筛选器、状态提示、证据说明和 PDF 报告必须支持中英文切换。数据库字段和内部枚举可保留英文，但展示层不得直接暴露难以理解的内部代码。
5. 每张图表下方必须提供简短解释，至少说明图表回答的问题、指标口径与分母、正确解读方式、样本或数据覆盖限制。
6. 百分比必须能查看分子、分母和样本量；样本不足的对象不得进入严重问题排名。缺失值不得自动转换为 0，缺失拓扑不得包装成可定位的网络热点。
7. “问题 App”不能继续采用“差体验用户占比大于 0”或“周期内任意一次异常”作为唯一判定。必须区分差体验观测占比、曾受影响用户占比、持续差体验用户占比和严重差体验用户占比。
8. 体验指标阈值、持续异常判定阈值、App 最低样本量和问题 App 门槛必须可配置并版本化；每个分析运行必须记录使用的阈值版本，以便复核和重跑。
9. 新分析流程不能只覆盖“总览 → 问题 App → App 详情”一条路径，必须支持从 App、用户、Cable/FTTH、时间、网络位置、家庭/用户侧、Server IP/内容源、容量与使用、数据可信度等维度交叉发现和下钻。
10. 任意分析入口应遵循统一深度：整体状态 → 比较与异常 → 影响对象 → 原因与证据 → 行动与复验。跨页面下钻必须保留当前 App、接入制式、时间、问题指标等上下文。
11. 首页应优先提供可解释的自动发现和调查入口，不要求用户从大量孤立图表中自行拼结论；所有自动发现必须包含影响范围、比较基线、主要驱动、数据可信度和可下钻证据。
12. 新版多维分析需要复用已导入 RAW 批次，重新设计标准 DWD、多维 DWS 和调查型 ADS；不得要求用户重新上传已经成功进入 RAW 的 3.46 GiB CSV，也不得让看板直接扫描 RAW。
13. 新聚合至少应评估 App×时间、App×接入制式、App×问题指标、用户×App持续性、网络节点×App、网络节点×时间、Server IP×App、批次间对比和数据覆盖等关系；最终范围需在分析流程评审后确认。
14. 聚合性能设计必须避免为每张看板重复扫描 RAW/DWD。应复用标准中间层，一轮任务生成相关 DWS/ADS，并继续提供子阶段、心跳、耗时、失败和安全重跑能力。
15. 当前是离线批次分析工作台，不得把批次趋势包装成实时监控、预测告警或闭环自动化；这些能力只有在新增连续数据源和验证机制后才能进入范围。

## 4. MVP 验收口径

- 工程可按 `npm install`、`npm run dev`、`npm run build`、`npm run tauri:dev` 路径继续验证。
- 数据库存在 metadata / dim / raw / dwd / dws / ads 分层 DDL。
- 前端存在导入、ETL、看板、Lead 分层的入口骨架。
- Tauri command 已提供后续接入 MySQL / CSV / ETL 的接口名称。
- SQL 模板不使用 `SET @var`，优先使用 CTE 参数块。
- 乱序但可映射的 CSV 表头仍应走 `LOAD DATA LOCAL INFILE`；1 GB+ 性能必须以目标硬件真实基准测试为准。
- `ads_network_hotspot_rank` 在 utf8mb4 下必须使用不超过 InnoDB 3072 字节限制的主键和索引设计。
- 数据画像和质量检查必须读取当前批次物理表，不得误读空的共享 RAW 基表。
- `LOAD DATA LOCAL INFILE` 必须实际传输非空客户端数据；路径白名单必须覆盖“允许当前文件、拒绝其他文件”的测试。
- 大文件 RAW 导入期间至少每 5 秒产生一次后端心跳，30 秒无字节变化时必须给出阶段性诊断提示。
- RAW 质量检查、CLEAN/DWD、DWS/ADS 等长步骤至少每 15 秒产生一次存活心跳；前台不得并发执行多个日志轮询请求，也不得重复展示同一 sequence。
- 选择历史批次后必须恢复该批次最新流水线的状态与日志，并以对应 `analysis_run_id` 查询看板；空结果和全 0 KPI 不得通过看板成功验收。
- 复用批次必须在后端验证 RAW/Quality/CLEAN 前置状态，同批次活动 SQL 存在时拒绝续跑，且完整生成五类结构化 ADS。
- 常规批次准备、Registry 和 Module Ready 不执行批次 RAW/DWD 大表精确全表计数；可用性验证使用有界查询。
- 全部图表导出不得在进入看板或切换页面时自动查询；只有用户启动后才顺序读取 6 个聚合数据集。报告应包含六类看板的全部非空图表、批次/运行/筛选元数据和空图/失败摘要，且不包含证据明细表。
- 仅配置 FTTH 网段且规则版本将 `Others` 显式配置为 Cable 时，CLEAN 结果不得继续产生因未命中规则导致的 UNKNOWN 接入类型；新规则草稿未配置 `Others` 时不得发布，旧聚合存在 UNKNOWN 时必须提示重跑 CLEAN/DWS/ADS。
- Game RAW 不存在时，Game Hours / MOS 不得显示为有效的 0；Lead 分层计数必须与完整 ADS 表按用户聚合结果一致。
## 1.0.50 implemented analysis workflow

- The primary path is `Experience Status → Auto Findings → Investigation Workspace → Saved Investigation`; legacy dashboards remain compatibility entries.
- Analysis Context persists App, access type, date/hour, issue metric/side, user, Server IP, BRAS, baseline and Finding across pages, with chips, remove, clear and back.
- Findings require sufficient samples and versioned policy thresholds. Every displayed rate retains numerator, denominator, sample size and policy version; missing and insufficient values are not zero.
- Investigation reads period and hourly DWS/ADS only. Network-side and user-side labels are evidence judgements, never confirmed root causes.
- Server-IP investigation is App/Finding-scoped and bounded to 200 priority users plus 20,000 DWD observations; it never scans RAW or creates an unbounded exploded IP fact table.
- Verification compares an analysis run only with an earlier successful run carrying identical access, Others, App-mapping and experience-policy versions; otherwise the UI reports that no comparable baseline exists.
- Batch selection must prefer the latest successful/degraded analyzable run and expose an explicit run selector with Period V2, App ADS and Hourly readiness. A manually generated run must not be hidden by an older pipeline run.
- V2 status, findings, coverage and verification load independently; one failed auxiliary dataset must not erase successful results, and a run without V2 rows must be identified as a context mismatch rather than an empty business result.
- Experience Policy and App Experience Profile drafts are editable and published as immutable versions. New runs bind and snapshot the published version.
- Game not imported, topology unavailable, identity limited and Server-IP controlled drill-down are distinct coverage states.
- Experience Findings and Cable-to-Fiber experience opportunities are separate; formal marketing eligibility requires external CRM/coverage/plan/arrears/blacklist/reachability data.
